ZEROFORM — ARCHITECTURAL & PROTOCOL SPECIFICATION

1. Coordinate Conventions

The visual workbench displays 1-based user coordinates $(r \in [1, R], c \in [1, C])$ familiar to mathematicians and engineers. The frontend automatically translates these into 0-based indices $(r \in [0, R-1], c \in [0, C-1])$ before submitting requests to the backend API and C CLI engine.

2. Triplet Representation (DOK)

A sparse matrix stores only its nonzero elements as a dynamic array of triplets: 

typedef struct {
    size_t row;
    size_t col;
    double value;
} Triplet;

Entries are kept in canonical row-major sorted order. Reading an implicit zero coordinate returns 0.0 in $O(\log \text{NNZ})$ time via binary search.

3. Theoretical Memory Payload Model

  • Dense Theoretical Payload: $\text{Total Cells} \times 8\text{ bytes}$ (flat contiguous IEEE 754 double array).
  • Sparse Theoretical Payload: $\text{NNZ} \times 16\text{ bytes}$ (fixed theoretical assumption: two 32-bit indices + 8-byte double).
  • Breakeven Point: Sparse representation consumes less theoretical memory when $\text{density} < 50\%$. Payloads are equal at exactly 50%.
  • Runtime C Storage vs Theoretical Model: While the course theoretical model evaluates idealized algorithmic payload sizes (16 bytes per nonzero entry), actual compiled C in-memory storage allocates dynamic array capacity multiplied by sizeof(Triplet) (where sizeof(Triplet) = 24 bytes on 64-bit platforms due to 64-bit size_t coordinates), together with matrix metadata (dimensions, count, capacity, data pointer) and dynamic array header structures. Actual process memory also entails heap allocation headers and OS runtime page overhead that the theoretical model does not measure.

4. Process Isolation & Subprocess Boundary

Python and Flask never perform matrix arithmetic. All data structures and linear algebra algorithms execute strictly within the compiled C11 engine (zeroform.exe) via a deterministic line-oriented protocol over stdin and stdout.
